In Progress: Extending

We use Flipper and Flipper::UI to provide Feature Flags to the business as a way to toggle some pieces of functionality at their discretion, and without developer intervention. However, the current implementation of Flipper's Instrumentation is stateless and broadcasts for every event of all features. This may work for the gem's general scope but for our use case I wanted to isolate our logic. The results have been very effective and I will be breaking the extensions that I made into my first 3 gems:

  1. Custom Features

    The Open/Closed Principle inspired me to emulate Rails' Single Table Inheritance sti_class_for(type_name) method. This allowed us to inform and memoize new Custom Feature subclasses within Flipper and allow subscribers to only scribe to a specific feature's events.

  2. Feature State Changes

    Custom Feature subclasses then opened the door to introduce the ability to let subscribers subscribe to only a Feature's state change events.

  3. ActiveSupport Subscriber / Responder

    Feature State Change and Custom Feature subclasses together and individually provide options for subscribing only to the desired operation events of applicable Features, instead of all of them. This drastically reduces the number of events that a subscriber needs to parse, reducing complexity, while also encapsulating event response logic for reuse in other Features. Additionally, Feature subclasses also made it easy to organize and share ActiveSupport::Notifications subscription response objects with the desired Feature subclasses.
